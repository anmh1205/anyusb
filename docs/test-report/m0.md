## Findings that affect the design

- A plain USB/IP import carries a busid and provides no AnyUSB pairing identity.
  The API can refuse a second lease and the host can scope TCP 3240 by network
  identity. The default raw backends cannot enforce a device-specific lease for
  multiple routable peers. See the [TCP 3240 design](../architecture.md#tcp-3240-access-by-backend).
  [Linux protocol](https://docs.kernel.org/usb/usbip_protocol.html), [Debian usbipd manual](https://manpages.debian.org/bookworm/usbip/usbipd.8.en.html)
- Windows persists a bind against a device instance ID. The Linux 6.8 stub
  also has a busid match table that can retain a matching entry after removal.
  Reconcile the actual export state before reissuing a bind. Persistence across
  each tested board's reset or identity change remains UNVERIFIED.
  [Windows bind persistence](https://github.com/dorssel/usbipd-win/blob/v5.3.0/Usbipd/UsbipdRegistry.cs), [Linux disconnect implementation](https://github.com/torvalds/linux/blob/v6.8/drivers/usb/usbip/stub_dev.c)
- usbip-win2 documents a 30-second first driver retry after disconnection.
  That retry cannot meet the few-second target on its own. Reconnect needs
  lease validation, fresh enumeration and a coordinated retry path.
  [usbip-win2 retry documentation](https://github.com/vadimgrn/usbip-win2/wiki/How-automatic-reattachment-works)
- Espressif documents that its TCP socket and RFC2217 serial URLs cannot
  exercise native USB support. Host-local esptool remains the plan for Remote
  ESP Ops. The local v5.2.0 CLI uses `--after hard-reset`, while the v4 spelling
  in the original test request is `--after hard_reset`.
  [Espressif remote serial limitations](https://docs.espressif.com/projects/esptool/en/latest/esp32s3/remote-serial-ports.html), [esptool reset options](https://docs.espressif.com/projects/esptool/en/latest/esp32s3/esptool/advanced-options.html)
